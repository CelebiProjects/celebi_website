# Extending a Workflow

This tutorial demonstrates how to extend an existing **Celebi workflow** by adding a second filtering task (`filter1`) after `filter0`.

We will also introduce how to safely rename and reorganize tasks within a Celebi project.

By connecting multiple tasks, we can build a longer analysis pipeline while keeping the analysis code local and intermediate data on the remote server.

## 1. Create a New Filter Task

Starting from the project created in the previous tutorial, create a new task in the project root:

```celebi
>>>> create-task filter1
>>>> cd filter1
```

Create a Python script named `filter1.py` inside the `filter1` directory.

Configure its `celebi.yaml` file:

```yaml
descriptor: filter1
environment: env_root_6.38.04
memory_limit: 256Mi

commands:
  - python3 filter1.py
```

The new task is designed to perform an additional processing step on the output of `filter0`.

## 2. Connect Tasks

### 2.1 Add the upstream task as input

In the `filter1` directory, run:

```celebi
>>>> add-input ../filter0 data_filter0
```

This creates a dependency between the two tasks:

```text
Raw Data
   |
   v
 filter0
   |
   v
 filter1
```

Here:

- `../filter0` refers to the upstream task.
- `data_filter0` is the input alias used by `filter1`.

The output of `filter0` becomes the input of `filter1`.

### 2.2 Input and output directories

From the perspective of `filter1.py`, the relevant paths are:

| Purpose | Directory |
|---|---|
| Input from `filter0` | `data_filter0/stageout/` |
| Output from `filter1` | `stageout/` |

For example:

```python
import ROOT
from pathlib import Path

input_file = ROOT.TFile.Open("data_filter0/stageout/output.root")

Path("stageout").mkdir(exist_ok=True)
output_file = ROOT.TFile("stageout/filtered.root", "RECREATE")

# Add your filtering code here.

output_file.Close()
input_file.Close()
```

Replace `output.root` with the actual output filename generated by `filter0`.

**Important:** Celebi manages the connection between tasks, so intermediate files do not need to be manually downloaded and transferred between processing steps.

## 3. Configure and Run the Task

### 3.1 Configure the runner

Enable remote caching and assign the runner:

```celebi
>>>> cache-on-runner on
>>>> request-runner pkufarm212
```

To avoid repeating these settings for every new task, configure your user-level
defaults with `user-config`. They are copied into tasks created afterwards; changing
them does not rewrite existing tasks and does not create project-wide defaults.


### 3.2 Verify the configuration

Run:

```celebi
>>>> ls
```

The output should contain information similar to:

```text
o--> Predecessors:
[0] (task)       data_filter0: @/filter0

Environment: env_root_6.38.04
Cache on runner: True
Default runner: pkufarm212
```

Check that the predecessor is correctly connected and that the environment and runner are configured as expected.

### 3.3 Submit the task

Submit `filter1` to the remote runner:

```celebi
>>>> submit --runner pkufarm212
```

Celebi uses the task dependency graph to determine the required upstream results.

If an upstream result is unavailable or needs to be regenerated, the workflow may need to execute the corresponding upstream task. Previously cached results can be reused when valid and available.

Monitor execution using:

```celebi
>>>> status
>>>> log -f
```

## 4. Visualize the Extended Workflow

To visualize the dependencies between tasks, run:

```celebi
>>>> draw-dag
```

The resulting graph shows how data flows from the original input through the filtering tasks.

![Extended Celebi workflow](https://github.com/user-attachments/assets/77211ea5-9418-4e06-82a0-fd3a36e300e7)


By following the same approach, you can build not only longer sequential pipelines but also more complex workflows structured as **directed acyclic graphs (DAGs)**. Tasks can have multiple inputs and dependencies, allowing different processing branches to run independently and their results to be combined in subsequent steps.

Each task can have its own Python script, execution environment, and input dependencies, providing the flexibility to design workflows for more sophisticated analyses.

**Note:** Task impressions identify specific versions of task configurations and their dependencies. When submitting a workflow, Celebi can reuse valid existing results rather than repeating every processing step. New impressions are generated when required by changes to the relevant tasks or their dependencies.

## 5. Manage Tasks and Directories

As a workflow grows, managing its directory structure becomes increasingly important.

**Always use Celebi commands to rename or move registered tasks.** Directly renaming or moving task directories in an IDE or file manager may break the relationships maintained by Celebi.

### 5.1 Rename a task

To rename `filter0` to `filter`, run the following command from the project root:

```celebi
>>>> mv filter0 filter
```

Here:

- `filter0` is the original task name.
- `filter` is the new task name.

Do not rename registered tasks directly in VS Code or another IDE.

### 5.2 Create a directory

To organize a large project, use Celebi's `mkdir` command. It creates a registered
directory object rather than an ordinary untracked folder:

```celebi
>>>> mkdir filters
```

Directories can be used to group related tasks.

### 5.3 Move a task into a directory

To move the task `Raw` into the directory `filters`, run:

```celebi
>>>> mv Raw filters/
```

The resulting structure is:

```text
B02K3pi/
├── filters/
│   └── Raw/
├── filter/
└── filter1/
```

The `mv` command should also be used when moving tasks out of a directory, moving directories or reorganizing the project.

### 5.4 Important precautions

When managing a Celebi project:

- Use `mv` within Celebi to rename or relocate registered tasks and directories.
- Avoid manually changing the locations of registered tasks in an IDE.
- Use `mkdir` to create organizational directories.
- Use `draw-dag` to confirm that the workflow structure remains correct.

If unexpected dependency or configuration problems occur, contact the Celebi maintainer, Mingrui Zhao (mingrui.zhao@mail.labz0.org).

## 6. Summary

A Celebi workflow can be extended by connecting the output of one task to the input of another.

The key command is:

```celebi
>>>> add-input ../filter0 data_filter0
```

This establishes a dependency between tasks while allowing each processing step to be developed independently.

The main advantages are:

- **Modularity:** Each task performs a separate analysis step.
- **Automatic dependency management:** Celebi tracks the relationships between tasks.
- **Remote data processing:** Large intermediate files remain on the server without requiring manual transfers.
- **Result reuse:** Cached outputs can avoid unnecessary repeated computations.
- **Flexible organization:** Tasks can be grouped and reorganized using Celebi commands.

With these features, you can gradually extend a simple filtering task into a complete physics analysis workflow.
